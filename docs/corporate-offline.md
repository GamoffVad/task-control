# Автономное развёртывание в корпоративной сети

Приложение не загружает шрифты, скрипты, стили или изображения из интернета. Клиент обращается только к собственному адресу `/api`. Данные хранятся в локальном Microsoft SQL Server; без его настроек сервер использует файл рядом с собой.

Стили рассчитаны на Google Chrome 109 — последнюю версию, которая работает на Windows 7, — и на все более новые браузеры.

## Хранилище: Microsoft SQL Server

Приложение работает с Microsoft SQL Server 2016 и новее; проверено на SQL Server 2025. **База и таблицы создаются сами при первом запуске** — на сервере достаточно завести учётную запись и указать её в настройках.

### 1. Учётная запись SQL Server

**Обычный путь — ничего делать вручную не нужно.** Шаг 7 файла `deploy-iis.bat` сам создаёт учётную запись приложения и базу, а затем вписывает их в `web.config`. Он выполняется от имени администратора, который запустил публикацию, поэтому у этой учётной записи Windows должны быть права `sysadmin` или `securityadmin` и `dbcreator` в SQL Server. Имя сервера, базы и учётной записи задаются переменными `SQLSERVER`, `SQLDB` и `SQLLOGIN` в первых строках батника.

Тот же шаг можно выполнить отдельно — например, если SQL Server подняли позже публикации:

```bat
powershell -ExecutionPolicy Bypass -File setup-sql.ps1 -Server SQLSRV -Database TaskControl -ConfigPath C:\inetpub\wwwroot\PLAN\web.config
```

Скрипт лежит и в комплекте (`dist-iis\setup-sql.ps1`, после публикации — рядом с сервером), и в папке `scripts` проекта. Повторный запуск безопасен: существующие учётную запись, базу и пароль он не трогает. Ключ `-Reset` задаёт учётной записи новый пароль, если прежний потерян. Пароль создаётся случайным и нигде не показывается — он сразу попадает в `web.config`. Там же создаётся `AUTH_SECRET`, если он пуст.

Если политика запрещает такую автоматику, сделайте то же вручную и запустите публикацию с ключом `/nosql`:

```sql
create login tc_app with password = N'<длинный пароль>';
create database TaskControl;
alter authorization on database::TaskControl to tc_app;
```

В SQL Server должен быть включён смешанный режим проверки подлинности. Серверная роль `dbcreator` приложению не нужна: базу создаёт скрипт настройки и делает учётную запись её владельцем. Если базу не создавать заранее, приложение создаст её само — тогда учётной записи нужна роль `dbcreator`.

### 2. Настройки приложения

```text
MSSQL_SERVER=SQLSRV
MSSQL_DATABASE=TaskControl
MSSQL_USER=tc_app
MSSQL_PASSWORD=<пароль>
AUTH_SECRET=<длинная случайная строка>
```

При публикации в IIS они лежат в разделе `appSettings` файла `web.config` и заполняются шагом 7 автоматически; вручную их правят, только если настройка выполнялась без него. Именованный экземпляр указывается прямо в имени сервера — `SQLSRV\BUH` — или отдельной переменной `MSSQL_INSTANCE`; нестандартный порт — `MSSQL_PORT`. Для входа доменной учётной записью вместо учётной записи SQL Server добавьте `MSSQL_DOMAIN` вместе с `MSSQL_USER` и `MSSQL_PASSWORD`.

Соединение шифруется; в корпоративной сети сертификат обычно самоподписанный, поэтому доверие к нему включено. Отключается переменными `MSSQL_ENCRYPT=false` и `MSSQL_TRUST_SERVER_CERTIFICATE=false`.

### 3. Что создаётся

При первом обращении приложение создаёт базу (если её нет) и 14 таблиц с префиксом `tc_`: задачи, события, нормы, отчёты, переписка, отметки прочтения, журнал уведомлений, словари, разделы плана, сотрудники, подразделения, шаблоны, роли и служебная `tc_meta`. Повторный запуск ничего не ломает: каждый оператор схемы защищён проверкой существования, а новые столбцы дописываются к уже существующим таблицам.

Изменения пишутся в транзакции под общей блокировкой `sp_getapplock`, поэтому одновременные правки разных сотрудников не теряются; при ошибке транзакция откатывается целиком.

### 4. Проверка

Адрес `GET /api/health` отвечает `{"ok":true,"storage":"sqlserver"}`, когда приложение работает с SQL Server и база отвечает. Ответ `"file"` означает, что настройки не подхватились и данные пишутся в файл. Код **503** и `{"ok":false,…,"error":"База данных недоступна."}` — настройки заданы, но подключиться не удалось: проверьте имя сервера, учётную запись и доступность SQL Server; подробная причина пишется в журнал `iisnode`.

## Публикация в IIS одним файлом

Сервер работает без интернета, поэтому ничего не скачивается и не собирается на нём: готовый комплект собирают заранее, на компьютере с интернетом, и привозят на носителе.

### Что привезти на сервер

Всё это скачивается один раз на компьютере с интернетом и переносится на съёмном носителе:

- архив `task-control-iis-<версия>.zip` — готовый комплект (папка `dist-iis`, `deploy-iis.bat`, эта инструкция);
- установщик Node.js 18 или новее для Windows (`.msi`);
- установщик модуля IIS [iisnode](https://github.com/Azure/iisnode/releases) (`.msi`);
- установщик модуля IIS [URL Rewrite](https://www.iis.net/downloads/microsoft/url-rewrite) (`.msi`).

Роль «Веб-сервер IIS» ставится из компонентов Windows и интернета не требует.

### Как получить архив

Папки `dist-iis` в репозитории нет: это результат сборки. На компьютере с интернетом, в папке проекта:

```bat
npm install
npm run pack:iis
```

Команда собирает комплект и кладёт архив `release\task-control-iis-<версия>.zip`. Он же приложен к каждому выпуску на GitHub (раздел Releases), так что на компьютере с интернетом его можно просто скачать, ничего не собирая.

### Публикация на сервере

1. Распакуйте архив в любую папку на сервере.
2. В первых строках `deploy-iis.bat` проверьте адрес (`IP`), порт (`PORT`) и имя SQL Server (`SQLSERVER`).
3. Запустите `deploy-iis.bat` от имени администратора из распакованной папки. Исходников проекта рядом нет, и батник сам берёт готовую папку `dist-iis`; ключ `/nobuild` указывать не нужно.

Если рядом нет ни исходников, ни `dist-iis`, батник так и скажет и напомнит, как получить архив.

**Что он делает по шагам:**

1. Проверяет права администратора, наличие `appcmd.exe`, `node.exe`, iisnode и URL Rewrite. Если чего-то не хватает, останавливается с понятным сообщением.
2. Берёт готовый комплект `dist-iis`. Если рядом лежат исходники (папка `node_modules`), собирает его заново (`npm run build:iis`); ключ `/nobuild` отключает сборку.
3. Копирует файлы в `C:\inetpub\wwwroot\PLAN`. При первой публикации создаёт `web.config` и записывает в него найденный путь к `node.exe`.
4. Выдаёт права: `IIS_IUSRS` — чтение всей папки, запись в `data` и `iisnode`; то же для учётной записи пула.
5. Создаёт пул приложений **PLAN**: без управляемого кода, `startMode=AlwaysRunning`, без простоя и перезапусков по расписанию — сервер Node.js держится постоянно.
6. Создаёт сайт **PLAN** с привязкой `http://10.199.127.27:1500` и назначает ему пул.
7. Включает Windows-аутентификацию, отключает анонимную и обычную, ставит `Negotiate` выше `NTLM`, добавляет правило с серверной переменной `HTTP_X_WINDOWS_USER` = `{LOGON_USER}`.
8. Настраивает SQL Server: создаёт учётную запись приложения со случайным паролем и базу, делает учётную запись её владельцем и вписывает настройки в `web.config` вместе с `AUTH_SECRET`. Пропускается ключом `/nosql`; ключ `/resetsql` задаёт новый пароль.
9. Открывает порт в брандмауэре и запускает пул и сайт.

**После публикации** настройки в разделе `appSettings` файла `C:\inetpub\wwwroot\PLAN\web.config` уже заполнены: сервер, база, учётная запись и `AUTH_SECRET`. IIS перезапускает приложение при сохранении файла. Проверка: `http://<адрес>:<порт>/api/health` должен вернуть `{"ok":true,"storage":"sqlserver"}`.

**Обновление до новой версии:** привезите новый архив, распакуйте и снова запустите `deploy-iis.bat`. `web.config`, папка `data` с хранилищем и папка `iisnode` с журналами не перезаписываются и не удаляются, поэтому настройки и данные сохраняются.

Адрес, порт, имя сайта и папку задают переменные в первых строках батника. В комплекте: `server.cjs` — сервер приложения, `public\` — интерфейс, `web.config` — настройки IIS, `setup-sql.ps1` — настройка SQL Server, `data\` — файловое хранилище, `README.txt` — краткая памятка.

## Бесшовный Windows-вход

Схема: браузер сотрудника → IIS с Windows Authentication → локальный Node.js-сервер приложения. Само приложение пароль не спрашивает и не отправляет `WWW-Authenticate`: доменного пользователя подтверждает IIS и передаёт заголовком.

### 1. Сервер приложения

Разместить IIS и сервер приложения внутри домена. Порт Node.js не публиковать для рабочих станций: запросы должны проходить только через IIS, иначе заголовок с именем пользователя сможет подделать любой, кто доберётся до порта.

### 2. IIS

1. Включить Windows Authentication, отключить Anonymous и Basic Authentication.
2. В «Providers» поставить `Negotiate` выше `NTLM`.
3. Передать имя пользователя приложению. При публикации через iisnode заголовки `X-iisnode-LOGON_USER` и `X-iisnode-AUTH_USER` добавляются сами. При публикации через ARR / URL Rewrite нужно правило исходящего запроса:

```xml
<rewrite>
  <allowedServerVariables>
    <add name="HTTP_X_WINDOWS_USER" />
    <add name="HTTP_X_WINDOWS_AUTH_SECRET" />
  </allowedServerVariables>
  <rules>
    <rule name="Windows user to app" stopProcessing="false">
      <match url=".*" />
      <serverVariables>
        <set name="HTTP_X_WINDOWS_USER" value="{LOGON_USER}" />
        <set name="HTTP_X_WINDOWS_AUTH_SECRET" value="общий-секрет" />
      </serverVariables>
      <action type="None" />
    </rule>
  </rules>
</rewrite>
```

Прокси обязан перезаписывать эти заголовки, а не дополнять: клиентские значения с теми же именами должны быть отброшены.

Сервер принимает доменного пользователя в любом из заголовков: `x-windows-user`, `x-iisnode-logon_user`, `x-iisnode-auth_user`, `x-iis-user`, `x-remote-user`, `x-forwarded-user`, `remote-user`, `auth-user`. Свой заголовок задаётся переменной `WINDOWS_AUTH_HEADER` и проверяется первым.

### 3. Переменные окружения сервера приложения

```text
WINDOWS_AUTH_TRUST_PROXY=true
WINDOWS_AUTH_HEADER=x-windows-user
WINDOWS_AUTH_PROXY_SECRET=<длинный случайный секрет>
```

`WINDOWS_AUTH_TRUST_PROXY=true` обязателен: без него приложение игнорирует заголовки и Windows-вход не работает, даже если переключатель в администрировании включён. `WINDOWS_AUTH_HEADER` и `WINDOWS_AUTH_PROXY_SECRET` необязательны, но секрет стоит задать: тогда запрос без совпавшего секрета в заголовке `X-Windows-Auth-Secret` к входу не допускается. После изменения переменных сервер нужно перезапустить.

### 4. Групповая политика браузера

Через групповую политику Chrome или Edge добавить внутреннее имя приложения в `AuthServerAllowlist` (и, если используется делегирование, в `AuthNegotiateDelegateAllowlist`). Альтернатива — поместить адрес в зону локальной интрасети. Без этого браузер покажет собственное окно ввода логина и пароля.

### 5. Сопоставление сотрудников

Доменный логин указывается в карточке сотрудника: **Администрирование → Сотрудники → Редактировать → Windows-логин**. Сервер сравнивает значение из заголовка в трёх формах: `DOMAIN\ivanov`, `ivanov@corp.local` и `ivanov`, регистр не важен. Сотруднику без заполненного логина Windows-вход не сработает.

### 6. Проверка настройки

**Администрирование → Аутентификация → Проверка Windows-входа → «Проверить настройку»** показывает, что сервер увидел в текущем запросе: включено ли доверие прокси, совпал ли секрет, какие заголовки пришли, какой логин из них взят и с каким сотрудником сопоставлен. Если что-то не так, выводится конкретная причина. Проверку можно запускать и до переключения режима.

Переключатель режима доступен всегда. При неверной настройке прокси приложение не блокирует вход: пока сервер не видит доменного пользователя в самом запросе, форма с логином и паролем продолжает работать, поэтому администратор не может запереть себя и сотрудников снаружи.

## Поиск пользователей в Active Directory

Выпадающий список ФИО из каталога включается отдельно и для Windows-входа не обязателен: сотрудников можно заводить вручную. На сервере установить RSAT-модуль `ActiveDirectory` и разрешить сервисной учётной записи чтение каталога. Затем задать:

```text
AD_SEARCH_ENABLED=true
AD_SEARCH_BASE=OU=Employees,DC=corp,DC=local
AD_POWERSHELL_PATH=powershell.exe
```

`AD_SEARCH_BASE` необязателен. Без него поиск выполняется по доступной области домена. Поиск запускается локально через `Get-ADUser`, ограничен 20 результатами и не использует внешние API или npm-модули.

## Проверка перед вводом в эксплуатацию

- «Проверить настройку» в администрировании показывает найденный заголовок, логин и сопоставленного сотрудника.
- Открытие приложения на доменном компьютере сразу приводит в календарь.
- Браузер не показывает диалог ввода имени и пароля.
- В администрировании статусы Windows и Active Directory отображаются как готовые.
- Поиск по первым буквам фамилии возвращает ФИО, должность и доменный логин.
- `GET /api/health` отвечает `storage: sqlserver`, а в базе появились таблицы `tc_`.
- Прямой доступ к порту Node.js с рабочих станций закрыт.
- DNS, IIS, Active Directory и база данных доступны без выхода в интернет.
