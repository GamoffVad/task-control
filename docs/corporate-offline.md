# Автономное развёртывание в корпоративной сети

Приложение не загружает шрифты, скрипты, стили или изображения из интернета. Клиент обращается только к собственному адресу `/api`. Без `DATABASE_URL` сервер использует локальный файл `.data/dev-db.json`; для нескольких серверов следует подключить внутренний PostgreSQL.

## Установка в IIS с SQL Server

1. На компьютере разработчика (Windows x64, с установленными зависимостями проекта) запустить `publish-iis.bat`. Получится автономный пакет `deploy/out/Plan-IIS` и архив `deploy/out/Plan-IIS-<версия>.zip`: интерфейс, сервер API, Node.js, драйвер SQL Server, схема базы и установщик. Скачивать на сервере ничего не нужно.
2. Перенести пакет на сервер и запустить `install.bat` от имени администратора (он же — sysadmin в SQL Server). По умолчанию: сайт `Plan` на порту 1500, папка `C:\inetpub\wwwroot\Plan`, база `Plan` в локальном SQL Server самой новой версии. Параметры — в `README.txt` пакета (`install.bat -Port 1600 -SqlServer .\SQLEXPRESS`).
3. Установщик включает IIS и ASP.NET 4.x из состава Windows (без Windows Update), создаёт базу и таблицы (`db/schema.sql`), сайт и пул IIS, выдаёт учётной записи `IIS APPPOOL\Plan` доступ к базе по Windows-входу, открывает порт в брандмауэре и проверяет работу. Повторный запуск обновляет приложение; данные и ключ сеансов (`AUTH_SECRET` в `web.config`) сохраняются.

Как устроено: IIS отдаёт статику, модуль `bin/PlanHost.dll` запускает `App_Data/node/node.exe` с сервером API на 127.0.0.1 (порт снаружи недоступен), проксирует `/api/*` и перезапускает сервер при сбое. Журнал сервера — `App_Data/logs`. Windows-аутентификация IIS включается только для `/api/windows-login`; прокси сам передаёт подтверждённый логин и общий секрет, поэтому настраивать заголовки из следующего раздела не нужно.

## Бесшовный Windows-вход

Рекомендуемая схема: браузер сотрудника → IIS с Windows Authentication → локальный Node.js-сервер приложения.

1. Разместить IIS и сервер приложения внутри домена. Порт Node.js не публиковать для рабочих станций: запросы должны проходить только через IIS.
2. В IIS включить Windows Authentication, отключить Basic Authentication и поставить провайдер `Negotiate` выше `NTLM`.
3. После успешной Windows-аутентификации IIS/reverse proxy должен удалить одноимённые клиентские заголовки и добавить:
   - `X-Windows-User`: подтверждённый `sAMAccountName` или `DOMAIN\\login`;
   - `X-Windows-Auth-Secret`: общий секрет прокси и приложения.
4. На сервере приложения задать:

```text
WINDOWS_AUTH_TRUST_PROXY=true
WINDOWS_AUTH_HEADER=x-windows-user
WINDOWS_AUTH_PROXY_SECRET=<длинный случайный секрет>
```

5. Через групповую политику Edge добавить внутреннее имя приложения в `AuthServerAllowlist`. Альтернатива — корректно поместить адрес в зону локальной интрасети. Тогда доменная учётная запись передаётся автоматически, без окна логина браузера.

Приложение не отправляет `WWW-Authenticate` и не показывает собственную форму в режиме Windows. Если IIS или политика браузера настроены неверно, приложение выводит обычную ошибку внутри страницы, а не Basic Auth-диалог.

## Поиск пользователей в Active Directory

На сервере установить RSAT-модуль `ActiveDirectory` и разрешить сервисной учётной записи чтение каталога. Затем задать:

```text
AD_SEARCH_ENABLED=true
AD_SEARCH_BASE=OU=Employees,DC=corp,DC=local
AD_POWERSHELL_PATH=powershell.exe
```

`AD_SEARCH_BASE` необязателен. Без него поиск выполняется по доступной области домена. Поиск запускается локально через `Get-ADUser`, ограничен 20 результатами и не использует внешние API или npm-модули.

## Проверка перед вводом в эксплуатацию

- Открытие приложения на доменном компьютере сразу приводит в календарь.
- Браузер не показывает диалог ввода имени и пароля.
- В администрировании статусы Windows и Active Directory отображаются как готовые.
- Поиск по первым буквам фамилии возвращает ФИО, должность и доменный логин.
- Прямой доступ к порту Node.js с рабочих станций закрыт.
- DNS, IIS, Active Directory и база данных доступны без выхода в интернет.
