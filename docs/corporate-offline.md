# Автономное развёртывание в корпоративной сети

Приложение не загружает шрифты, скрипты, стили или изображения из интернета. Клиент обращается только к собственному адресу `/api`. Данные хранятся в локальном Microsoft SQL Server; без его настроек сервер использует файл рядом с собой.

Стили рассчитаны на Google Chrome 109 — последнюю версию, которая работает на Windows 7, — и на все более новые браузеры.

## Хранилище: Microsoft SQL Server

Приложение работает с Microsoft SQL Server 2016 и новее; проверено на SQL Server 2025. **База и таблицы создаются сами при первом запуске** — на сервере достаточно завести учётную запись и указать её в настройках.

### 1. Подключение к SQL Server

**Обычный путь — ничего делать вручную не нужно, учётная запись SQL Server не создаётся.** Пул приложений `PLAN` работает под учётной записью Windows того, кто запускает `deploy-iis.bat` (пароль батник спрашивает один раз, проверяет и передаёт IIS; повторная публикация его не спрашивает, после смены пароля Windows — ключ `/password`). Под этой же учётной записью приложение входит в SQL Server — вход Windows (`Trusted_Connection`, драйвер ODBC, он есть в любой Windows), поэтому в `web.config` строки `MSSQL_USER` и `MSSQL_PASSWORD` пустые. Шаг 7 создаёт базу, если её нет, и вписывает `MSSQL_SERVER` и `MSSQL_DATABASE`. У публикующего должен быть доступ к SQL Server и право создавать базы (`dbcreator` или `sysadmin`), если базы ещё нет. Имя сервера и базы задаются переменными `SQLSERVER` и `SQLDB` в первых строках батника.

Прежний способ — отдельная учётная запись SQL Server `tc_app` со случайным паролем в `web.config` — включается ключом `/sqllogin` (`/resetsql` — задать ей новый пароль).

Тот же шаг можно выполнить отдельно — например, если SQL Server подняли позже публикации:

```bat
powershell -ExecutionPolicy Bypass -File setup-sql.ps1 -Server SQLSRV -Database TaskControl -ConfigPath C:\inetpub\wwwroot\PLAN\web.config
```

Скрипт лежит и в комплекте (`dist-iis\setup-sql.ps1`, после публикации — рядом с сервером), и в папке `scripts` проекта. Повторный запуск безопасен: существующую базу и её данные он не трогает. Параметр `-WindowsAccount` — учётная запись пула, если она отличается от того, кто запускает скрипт: тогда ей выдаётся вход Windows в SQL Server и права владельца базы. Ключ `-SqlLogin` — прежний способ с учётной записью `tc_app` (`-Reset` — новый пароль). В `web.config` создаётся и `AUTH_SECRET`, если он пуст.

Если политика запрещает такую автоматику, сделайте то же вручную и запустите публикацию с ключом `/nosql`:

```sql
create login tc_app with password = N'<длинный пароль>';
create database TaskControl;
alter authorization on database::TaskControl to tc_app;
```

В SQL Server должен быть включён смешанный режим проверки подлинности. Серверная роль `dbcreator` приложению не нужна: базу создаёт скрипт настройки и делает учётную запись её владельцем. Если базу не создавать заранее, приложение создаст её само — тогда учётной записи нужна роль `dbcreator`.

### 2. Настройки приложения

```text
MSSQL_SERVER=SQLSRV
MSSQL_DATABASE=TaskControl
MSSQL_USER=tc_app
MSSQL_PASSWORD=<пароль>
AUTH_SECRET=<длинная случайная строка>
```

При публикации в IIS они лежат в разделе `appSettings` файла `web.config` и заполняются шагом 7 автоматически; вручную их правят, только если настройка выполнялась без него. Именованный экземпляр указывается прямо в имени сервера — `SQLSRV\BUH` — или отдельной переменной `MSSQL_INSTANCE`; нестандартный порт — `MSSQL_PORT`. Для входа доменной учётной записью вместо учётной записи SQL Server добавьте `MSSQL_DOMAIN` вместе с `MSSQL_USER` и `MSSQL_PASSWORD`.

Соединение шифруется; в корпоративной сети сертификат обычно самоподписанный, поэтому доверие к нему включено. Отключается переменными `MSSQL_ENCRYPT=false` и `MSSQL_TRUST_SERVER_CERTIFICATE=false`.

### 3. Что создаётся

При первом обращении приложение создаёт базу (если её нет) и 14 таблиц с префиксом `tc_`: задачи, события, нормы, отчёты, переписка, отметки прочтения, журнал уведомлений, словари, разделы плана, сотрудники, подразделения, шаблоны, роли и служебная `tc_meta`. Повторный запуск ничего не ломает: каждый оператор схемы защищён проверкой существования, а новые столбцы дописываются к уже существующим таблицам.

Изменения пишутся в транзакции под общей блокировкой `sp_getapplock`, поэтому одновременные правки разных сотрудников не теряются; при ошибке транзакция откатывается целиком.

### 4. Проверка

Адрес `GET /api/health` отвечает `{"ok":true,"storage":"sqlserver"}`, когда приложение работает с SQL Server и база отвечает. Ответ `"file"` означает, что настройки не подхватились и данные пишутся в файл. Код **503** и `{"ok":false,…,"error":"База данных недоступна."}` — настройки заданы, но подключиться не удалось: проверьте имя сервера, учётную запись и доступность SQL Server; подробная причина пишется в журнал `iisnode`.

## Публикация в IIS одним файлом

Сервер работает без интернета, поэтому ничего не скачивается и не собирается на нём: готовый комплект собирают заранее, на компьютере с интернетом, и привозят на носителе.

### Что привезти на сервер

Всё это скачивается один раз на компьютере с интернетом и переносится на съёмном носителе:

- архив `task-control-iis-<версия>.zip` — готовый комплект (папка `dist-iis`, `deploy-iis.bat`, эта инструкция);
- установщик Node.js 18 или новее для Windows (`.msi`);
- установщик модуля IIS [iisnode](https://github.com/Azure/iisnode/releases) (`.msi`);
- установщик модуля IIS [URL Rewrite](https://www.iis.net/downloads/microsoft/url-rewrite) (`.msi`).

Роль «Веб-сервер IIS» ставится из компонентов Windows и интернета не требует.

### Как получить архив

Папки `dist-iis` в репозитории нет: это результат сборки. На компьютере с интернетом, в папке проекта:

```bat
npm install
npm run pack:iis
```

Команда собирает комплект и кладёт архив `release\task-control-iis-<версия>.zip`. Он же приложен к каждому выпуску на GitHub (раздел Releases), так что на компьютере с интернетом его можно просто скачать, ничего не собирая.

### Публикация на сервере

1. Распакуйте архив в любую папку на сервере.
2. В первых строках `deploy-iis.bat` проверьте адрес (`IP`), порт (`PORT`) и имя SQL Server (`SQLSERVER`).
3. Запустите `deploy-iis.bat` от имени администратора из распакованной папки. Исходников проекта рядом нет, и батник сам берёт готовую папку `dist-iis`; ключ `/nobuild` указывать не нужно.

Если рядом нет ни исходников, ни `dist-iis`, батник так и скажет и напомнит, как получить архив.

**Что он делает по шагам:**

1. Проверяет права администратора и ставит недостающее: роли Windows Server (IIS, проверка подлинности Windows, консоль IIS, модуль Active Directory для PowerShell) — из состава системы, без интернета; Node.js, URL Rewrite и iisnode — тихо, установщиками `.msi` из папки `installers` рядом с батником. Если установщика нет, останавливается и называет нужный файл.
2. Берёт готовый комплект `dist-iis`. Если рядом лежат исходники (папка `node_modules`), собирает его заново (`npm run build:iis`); ключ `/nobuild` отключает сборку.
3. Показывает версию комплекта и версию на сервере, останавливает пул, копирует файлы в `C:\inetpub\wwwroot\PLAN`. При первой публикации создаёт `web.config`, записывает в него найденный путь к `node.exe` и включает поиск в Active Directory. В `web.config` прежних версий дописывает `promoteServerVars`.
4. Выдаёт права: `IIS_IUSRS` — чтение всей папки, запись в `data` и `iisnode`; то же для учётной записи пула.
5. Создаёт пул приложений **PLAN**: без управляемого кода, `startMode=AlwaysRunning`, без простоя и перезапусков по расписанию — сервер Node.js держится постоянно.
6. Создаёт сайт **PLAN** с привязкой `http://10.199.127.27:1500` и назначает ему пул.
7. Включает проверку подлинности Windows **вместе с анонимной** (обычная выключена), ставит `Negotiate` выше `NTLM` и удаляет правило `HTTP_X_WINDOWS_USER` прежних версий. Способ входа после этого переключается в самом приложении (**Администрирование → Аутентификация**), править IIS и `web.config` не нужно.
8. Настраивает SQL Server: создаёт базу, если её нет, и вписывает в `web.config` вход Windows учётной записью пула (без учётной записи SQL Server) вместе с `AUTH_SECRET`. Пропускается ключом `/nosql`; `/sqllogin` — прежний способ с учётной записью `tc_app`.
9. Открывает порт в брандмауэре, запускает пул и сайт и обращается к приложению: оно сверяет схему базы — создаёт недостающие таблицы, столбцы и индексы, не трогая данные. Тестовых данных нет: в пустой базе — справочники, роли, шаблоны и разделы плана, администратор — публикующий (`TC_ADMIN_LOGIN`). Батник проверяет, что приложение работает с SQL Server (`storage: sqlserver`) и что на сервере теперь версия комплекта.

**Повторная публикация данные не затирает.** При каждом запуске приложение сверяет схему с описанием таблиц: недостающие таблицы и столбцы (у обязательных — со значением по умолчанию для уже существующих строк) и индексы создаются, ничего не удаляется и не изменяется. Тестовых данных приложение не пишет никогда. `web.config` и папку журналов `iisnode` батник не перезаписывает. Хранилище — только SQL Server: без `MSSQL_SERVER` приложение не работает, `/api/health` отвечает 503.

**После публикации** настройки в разделе `appSettings` файла `C:\inetpub\wwwroot\PLAN\web.config` уже заполнены: сервер, база, учётная запись и `AUTH_SECRET`. IIS перезапускает приложение при сохранении файла. Проверка: `http://<адрес>:<порт>/api/health` должен вернуть `{"ok":true,"storage":"sqlserver"}`.

**Обновление до новой версии:** привезите новый архив, распакуйте и снова запустите `deploy-iis.bat`. `web.config`, папка `data` с хранилищем и папка `iisnode` с журналами не перезаписываются и не удаляются, поэтому настройки и данные сохраняются.

Адрес, порт, имя сайта и папку задают переменные в первых строках батника. В комплекте: `server.cjs` — сервер приложения, `public\` — интерфейс, `web.config` — настройки IIS, `setup-sql.ps1` — настройка SQL Server, `data\` — файловое хранилище, `README.txt` — краткая памятка.

## Публикация с другого компьютера сети

Публиковать можно с любого компьютера сети, на сервере ничего запускать не нужно. Комплект передаётся на сервер по PowerShell Remoting (WinRM), и там выполняется тот же `deploy-iis.bat` — шаги, ключи и результат те же, что при локальной публикации. Интернет не нужен.

```bat
deploy-iis-remote.bat -Server SRV-IIS
```

**Что нужно:**

- на компьютере, с которого публикуете, — распакованный архив `task-control-iis-<версия>.zip` (или проект с собранным `dist-iis`);
- учётная запись с правами **администратора на сервере** (по умолчанию — та, под которой вы вошли; другую можно ввести окном: `-AskCredential`);
- на сервере включён WinRM — в Windows Server он включён по умолчанию, иначе на сервере один раз: `Enable-PSRemoting -Force`; между компьютерами открыт порт 5985;
- на сервере установлены роль «Веб-сервер IIS», Node.js, iisnode и URL Rewrite — как и для локальной публикации.

**Что делает скрипт** (`scripts/deploy-remote.ps1`):

1. Подключается к серверу и показывает его состояние: права, роль IIS, модули iisnode и URL Rewrite, версия Node.js, версия приложения на сервере. Если чего-то не хватает, останавливается с понятным сообщением.
2. Упаковывает `dist-iis` и `deploy-iis.bat`, передаёт архив на сервер и распаковывает во временную папку.
3. Запускает на сервере `deploy-iis.bat`, выводит его сообщения и сохраняет их в файл `deploy-remote-<сервер>.log` рядом со скриптом.
4. Удаляет временную папку, показывает версию, которая теперь стоит на сервере, и проверяет `/api/health`.

**Параметры:**

| Параметр | Назначение |
|---|---|
| `-Server ИМЯ` | имя или адрес сервера IIS (если не указан, скрипт спросит) |
| `-Check` | только проверить сервер, ничего не публиковать |
| `-AskCredential` | войти другой учётной записью (окно логина и пароля) |
| `-NoSql` / `-ResetSql` | то же, что `/nosql` и `/resetsql` у `deploy-iis.bat` |
| `-Site`, `-Pool`, `-Ip`, `-Port`, `-Target` | имя сайта, пула, адрес, порт и папка на сервере, если они отличаются от значений в начале `deploy-iis.bat` |
| `-SqlServer`, `-SqlDb`, `-SqlLogin` | сервер, база и учётная запись SQL Server |
| `-Build` | пересобрать комплект из исходников на этом компьютере (нужны `npm install` и интернет) |

Пример: `deploy-iis-remote.bat -Server SRV-IIS -Ip 10.199.127.27 -Port 1500 -NoSql`.

**Если подключиться не удалось:** проверьте, что сервер включён и порт 5985 доступен; что на нём включён WinRM; что у вашей учётной записи есть права администратора (или укажите другую); для сервера вне домена или при указании адреса вместо имени добавьте его в доверенные на своём компьютере: `Set-Item WSMan:\localhost\Client\TrustedHosts -Value "СЕРВЕР"`.

**SQL Server на другом компьютере.** Скрипт выполняется на сервере IIS от имени вашей учётной записи, и передать её дальше, на третий компьютер, WinRM по умолчанию не может. Поэтому, если SQL Server стоит не на сервере IIS, создайте базу скриптом `scripts/create-database.sql` (следующий раздел) и публикуйте с ключом `-NoSql`.

## Скрипт базы данных SQL Server

Файл `scripts/create-database.sql` создаёт базу данных вручную — на случай, когда базу удобнее подготовить самому или SQL Server стоит на отдельном компьютере. Скрипт собирается из схемы приложения (`npm run build:sql`), поэтому всегда соответствует версии; тест следит, чтобы файл не отставал.

Что он делает: создаёт базу `TaskControl`, учётную запись SQL Server `tc_app` с вашим паролем, делает её владельцем базы (`db_owner`, чтобы приложение могло дополнять таблицы при обновлениях) и создаёт все 14 таблиц с индексами (префикс `tc_`). Повторный запуск безопасен: существующее не пересоздаётся, пароль уже созданной учётной записи не меняется.

**Как запустить:**

1. Откройте файл в SQL Server Management Studio под учётной записью с правами `sysadmin` (или `dbcreator` и `securityadmin`).
2. В разделе 2 замените `ЗАМЕНИТЕ_НА_СВОЙ_ПАРОЛЬ` на пароль учётной записи `tc_app`. Пока пароль не заменён, учётная запись не создаётся.
3. Выполните скрипт целиком (F5). Либо из командной строки: `sqlcmd -S СЕРВЕР -E -C -b -i create-database.sql`. В конце выводится список созданных таблиц.
4. В разделе `appSettings` файла `web.config` приложения укажите `MSSQL_SERVER` (имя сервера или `СЕРВЕР\ЭКЗЕМПЛЯР`), `MSSQL_DATABASE` (`TaskControl`), `MSSQL_USER` (`tc_app`), `MSSQL_PASSWORD` и `AUTH_SECRET` (любая длинная случайная строка — ключ подписи сеансов).
5. Публикуйте с ключом `/nosql` (`deploy-iis.bat /nosql` или `deploy-iis-remote.bat -Server СЕРВЕР -NoSql`), иначе `deploy-iis.bat` сам создаст учётную запись и пароль.
6. Проверьте `http://<адрес>:<порт>/api/health`: `"storage":"sqlserver"`.

Таблицы создаются пустыми. При первом открытии приложение записывает только справочники, роли, шаблоны и разделы плана; тестовых данных нет. Администратором становится учётная запись из `TC_ADMIN_LOGIN`, остальные сотрудники вносятся в «Администрировании».

Для другого имени базы или учётной записи замените `TaskControl` и `tc_app` во всём файле и укажите те же значения в `web.config`.

## Бесшовный Windows-вход

Схема: браузер сотрудника → IIS (анонимный доступ и Windows Authentication) → iisnode → Node.js-сервер приложения. Само приложение пароль не спрашивает и `WWW-Authenticate` не отправляет: когда нужен доменный пользователь (вход в режиме «Windows» и «Проверить настройку»), оно отвечает `401`, IIS добавляет к ответу запрос Windows-аутентификации, браузер повторяет запрос с доменной учётной записью, а iisnode передаёт подтверждённый логин заголовком `X-iisnode-LOGON_USER`.

**Вход — только через Windows.** Формы входа, паролей приложения и переключателя способа входа нет: сотрудник входит доменной учётной записью, которая должна быть в «Администрировании → Пользователи» (столбец «Windows-логин»). Если активного администратора в базе нет, администратором становится учётная запись из `TC_ADMIN_LOGIN` в `web.config` — её записывает `deploy-iis.bat` (это тот, кто публикует). Сеансы прежнего входа по паролю недействительны. Истёкший сеанс приложение отдаёт кодом `403`, чтобы IIS не запрашивал на него учётную запись Windows. Токен сеанса передаётся заголовком `X-TC-Token`, а не `Authorization`: этот заголовок нужен IIS для проверки подлинности Windows.

### 1. Сервер приложения

Разместить IIS и сервер приложения внутри домена. Порт Node.js не публиковать для рабочих станций: запросы должны проходить только через IIS, иначе заголовок с именем пользователя сможет подделать любой, кто доберётся до порта.

### 2. IIS

`deploy-iis.bat` делает всё это сам; вручную — так:

1. Включить Windows Authentication и Anonymous Authentication, отключить Basic Authentication.
2. В «Providers» поставить `Negotiate` выше `NTLM`.
3. Передать имя пользователя приложению. При публикации через iisnode заголовки `X-iisnode-LOGON_USER` и `X-iisnode-AUTH_USER` добавляет iisnode, если в `web.config` у элемента `<iisnode>` указано `promoteServerVars="LOGON_USER,AUTH_USER"` (комплект и `deploy-iis.bat` прописывают его сами). iisnode не заменяет одноимённый заголовок от браузера, а дописывает свой в конец, поэтому приложение берёт **последнее** значение заголовка и других заголовков не принимает (`WINDOWS_AUTH_HEADER=x-iisnode-logon_user` — значение по умолчанию для IIS).

При публикации через ARR / URL Rewrite (без iisnode) нужно правило исходящего запроса. Учтите, что правило URL Rewrite срабатывает до проверки подлинности, и при включённом анонимном доступе `{LOGON_USER}` в нём может быть пустым:

```xml
<rewrite>
  <allowedServerVariables>
    <add name="HTTP_X_WINDOWS_USER" />
    <add name="HTTP_X_WINDOWS_AUTH_SECRET" />
  </allowedServerVariables>
  <rules>
    <rule name="Windows user to app" stopProcessing="false">
      <match url=".*" />
      <serverVariables>
        <set name="HTTP_X_WINDOWS_USER" value="{LOGON_USER}" />
        <set name="HTTP_X_WINDOWS_AUTH_SECRET" value="общий-секрет" />
      </serverVariables>
      <action type="None" />
    </rule>
  </rules>
</rewrite>
```

Прокси обязан перезаписывать эти заголовки, а не дополнять: клиентские значения с теми же именами должны быть отброшены.

Если `WINDOWS_AUTH_HEADER` задан, сервер принимает доменного пользователя только из этого заголовка (последнее значение). Иначе — из любого из заголовков `x-windows-user`, `x-iisnode-logon_user`, `x-iisnode-auth_user`, `x-iis-user`, `x-remote-user`, `x-forwarded-user`, `remote-user`, `auth-user`; так можно работать только за прокси, который сам перезаписывает эти заголовки. Сервер для IIS (`server.cjs`) по умолчанию использует `x-iisnode-logon_user`.

### 3. Переменные окружения сервера приложения

```text
WINDOWS_AUTH_TRUST_PROXY=true
WINDOWS_AUTH_HEADER=x-iisnode-logon_user
WINDOWS_AUTH_PROXY_SECRET=<длинный случайный секрет>
```

`WINDOWS_AUTH_TRUST_PROXY=true` обязателен: без него приложение игнорирует заголовки и Windows-вход не работает, даже если переключатель в администрировании включён. `WINDOWS_AUTH_HEADER` и `WINDOWS_AUTH_PROXY_SECRET` необязательны, но секрет стоит задать: тогда запрос без совпавшего секрета в заголовке `X-Windows-Auth-Secret` к входу не допускается. После изменения переменных сервер нужно перезапустить.

### 4. Групповая политика браузера

Через групповую политику Chrome или Edge добавить внутреннее имя приложения в `AuthServerAllowlist` (и, если используется делегирование, в `AuthNegotiateDelegateAllowlist`). Альтернатива — поместить адрес в зону локальной интрасети. Без этого браузер покажет собственное окно ввода логина и пароля.

### 5. Сопоставление сотрудников

Доменный логин указывается в карточке сотрудника: **Администрирование → Сотрудники → Редактировать → Windows-логин**. Сервер сравнивает значение из заголовка в трёх формах: `DOMAIN\ivanov`, `ivanov@corp.local` и `ivanov`, регистр не важен. Сотруднику без заполненного логина Windows-вход не сработает.

### 6. Проверка настройки

**Администрирование → Аутентификация → Проверка Windows-входа → «Проверить настройку»** показывает, что сервер увидел в текущем запросе: включено ли доверие прокси, совпал ли секрет, какие заголовки пришли, какой логин из них взят и с каким сотрудником сопоставлен. Если что-то не так, выводится конкретная причина. Проверку можно запускать и до переключения режима.

Если сервер не видит доменного пользователя, войти нельзя: резервного входа по паролю нет. Причину покажет эта проверка и сообщение на экране входа.

## Поиск пользователей в Active Directory

Выпадающий список ФИО из каталога включается отдельно и для Windows-входа не обязателен: сотрудников можно заводить вручную. На сервере установить RSAT-модуль `ActiveDirectory` и разрешить сервисной учётной записи чтение каталога. Затем задать:

```text
AD_SEARCH_ENABLED=true
AD_SEARCH_BASE=OU=Employees,DC=corp,DC=local
AD_POWERSHELL_PATH=powershell.exe
```

`AD_SEARCH_BASE` необязателен. Без него поиск выполняется по доступной области домена. Поиск запускается локально через `Get-ADUser`, ограничен 20 результатами и не использует внешние API или npm-модули.

## Проверка перед вводом в эксплуатацию

- «Проверить настройку» в администрировании показывает найденный заголовок, логин и сопоставленного сотрудника.
- Открытие приложения на доменном компьютере сразу приводит в календарь.
- Браузер не показывает диалог ввода имени и пароля.
- В администрировании статусы Windows и Active Directory отображаются как готовые.
- Поиск по первым буквам фамилии возвращает ФИО, должность и доменный логин.
- `GET /api/health` отвечает `storage: sqlserver`, а в базе появились таблицы `tc_`.
- Прямой доступ к порту Node.js с рабочих станций закрыт.
- DNS, IIS, Active Directory и база данных доступны без выхода в интернет.
